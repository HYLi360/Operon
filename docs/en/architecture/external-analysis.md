# External analysis execution model

## Execution model

External programs such as BLAST/HMMER/BUSCO no longer require hand-assembled command lines. A recipe in `config/tools.yaml` declares the input category, artifact types, launch method, parameters, and result parser; the `analyze` command automatically:

1. Selects from the `files` manifest all inputs matching `entity_type + file_role + format`;
2. Verifies per `input_kind` that the input file or directory still exists and that its content hash matches the manifest;
3. Probes the program version (`version_args + version_pattern`) and records it in `analysis_jobs`;
4. Computes the reference database identity (single-file SHA-256 / directory fingerprint / explicit checksum);
5. Looks up a completed cache by `analysis_name + file_id + input SHA + parameter fingerprint + tool version + database identity`, skipping on a hit; on a miss, enters the second-level continuation: if an old `completed` job for the same `(analysis, file_id)` has a matching input content hash and its recorded output artifact passes byte-level verification, that output is adopted (a new `completed` row is inserted under the current fingerprint, traced in the `changes` audit table, with status `adopted`); only otherwise is the job recomputed;
6. On a miss, launches the program via `conda run`, a container prefix, or a direct path; both file and directory outputs must exist and be non-empty, with stdout/stderr written to disk;
7. Computes the file or directory content hash, parses top hits or the BUSCO JSON summary into `analysis_hits`/`analysis_results`, and syncs the same-named metrics into `qc_results`. Parsers with coordinates (`blast_tabular`, `hmmer_domtblout`, `rpsbproc_tabular`) additionally write every parsed hit to `analysis_alignments` as a structured row (query/subject IDs, hit rank, query/subject intervals, e-value, bitscore, percent identity, unmapped columns in `extra_json`), untruncated by `max_hits_per_query`; `report analysis --hits` reads this table.

Directories use a deterministic tree hash composed of relative paths, empty directories, file sizes/contents, and symlink targets. `database_mode: mutable_cache` serves shared caches such as BUSCO's that gradually download lineages, identified by an explicit `database_version` as the logical version; immutable reference databases keep the default `reference` content identity.

A recipe may replace the single command with a `commands` chain (mutually exclusive with `arguments`). All rendered steps execute in order through the same executor and parent-tool `run_method`, under one run record and one `analysis_jobs` row. A step invoking the parent `executable` inherits its already-probed version; another program may declare its own `version_args` and `version_pattern`, which are run through the same launcher/executor. Unconfigured secondary programs are explicitly recorded as version `unknown`; version flags are never guessed. Each step receives its own `logs/<run_id>.step<N>.stdout.log` / `.stderr.log`, and its `argv`, `executable`, `tool_version`, `tool_version_raw`, `version_source`, `version_command`, and `exit_code` are recorded in `execution_details.steps`. The first non-zero step aborts the chain and fails the job with a `step N/M failed` error. Intermediate artifacts live in a deterministic `${work_dir}` scratch directory (`<output_name>.work` next to the output), which is deleted and rebuilt before execution and removed after success or failure (`--keep-partial` keeps it). Expected-output validation, content hashing, and result parsing run once, after the last step. On SSH backends with a remote root the work directory is mapped to the remote root and created there like any other project path. The canonical example couples `rpsblast -outfmt 11` (ASN.1 archive) with independently versioned `rpsbproc`, whose tabular report is parsed by `rpsbproc_tabular`: domain rows from the `DATA`/`SESSION`/`QUERY`/`DOMAINS` blocks become full `analysis_alignments` rows (the query is the QUERY definition line, the subject is the accession, coordinates come from the `from`/`to` columns, and hit type/PSSM IDs/short name stay in `extra_json`), with EAV hits truncated to `max_hits_per_query` as usual. Step-level version collection is provenance-only and does not alter cache identity.

Actual execution of external commands is taken over by the backend abstraction in `execution.py`; `run_external_command` selects a backend through `get_executor(project, backend)`:

- `local` (default): the original local subprocess behavior, completely unchanged;
- `slurm`: a local Slurm cluster. Generates a `<run_id>.sbatch` batch script under `logs/` (`--cpus-per-task` takes the thread count; optional `--time`/`--partition`/`--mem`, `extra_sbatch`, and `setup_commands`), submits with `sbatch --parsable`, polls `squeue` at `poll_interval`, and after the job disappears reads the `<run_id>.exitcode` file written by the script (falling back to `sacct` on failure); requires the project directory to be on a filesystem shared with the compute nodes;
- `ssh`: executes on an SSH remote host (HPC head node / cloud VM) through the lazily imported Paramiko runtime dependency; with `execution.ssh.scheduler: slurm`, sbatch/squeue runs on the remote instead. Supports `remote_root` path mapping (empty means a shared filesystem); input files are uploaded over SFTP (identical content skipped, strict SHA-256/directory-tree hash, different content refused). When `storage_remote` is configured, REMOTE_ONLY inputs are consumed in place on the remote. Before a run, the exactly computed old remote output is removed; expected outputs are pulled back through temporary files and compared against the remote content again; an existing local output is accepted only when its content is identical. `storage_remote` and an explicit `remote_root` must point to the same root. One analysis batch uses a single lazy SSH client for version probing, remote input verification, database preflight, and all commands, closing it uniformly at the end. Direct commands run in a separate process group via util-linux `setsid --wait` (guaranteeing reliable exit-code return); on timeout, TERM/KILL is sent to the remote process group based on a restricted PID file, and when a termination request cannot be sent, the error and provenance state explicitly that the process may still be running. Remote Slurm polls strictly at `poll_interval` and retries the exitcode file that is briefly invisible after a job disappears.

All three backends share the same provenance and correctness contract: exit codes, start/end times, and logs are written to `workflow_runs` and `logs/workflow.jsonl` as usual; SQLite additionally stores the executor, scheduler job ID, and resource/script details; success determination and input/output SHA-256 verification are unchanged; tool version probing on non-`local` backends also goes through the same backend. An individual recipe can override same-named fields of `execution.slurm` with a `slurm:` mapping (e.g. adjusting memory/time for BUSCO alone).

Execution environment capture (schema 2.8, `environment.py`): all three backends probe the execution environment on every run. The normalized JSON document is stored in the `execution_environments` table; its primary key `environment_id` is the SHA-256 of that normalized JSON (content-addressed, so identical documents deduplicate automatically), and both `workflow_runs` and `analysis_jobs` reference it through their own `environment_id` column.

- `local`: collects hostname, OS/kernel/architecture, Python and `operon` versions, the environment variables `PATH`, `CONDA_PREFIX`, `CONDA_DEFAULT_ENV`, `VIRTUAL_ENV`, `SINGULARITY_NAME`, `APPTAINER_NAME`, `container`, and a docker probe, all directly;
- `slurm`: embeds the probe in the sbatch script, writes the result to `<run_id>.env` inside the job, and reads it back — the captured environment is the compute node's, not the submission host's;
- `ssh`: direct mode runs the probe on the remote host through paramiko; remote Slurm mode embeds and retrieves the same job-side probe so it also records the compute node rather than the SSH login node.

A failed probe leaves the run's `environment_id` NULL without raising an error or affecting the run; rows from before 2.8 are likewise NULL.

Recipe versioning and snapshots (schema 2.9): a recipe gains an optional `version:` field (a positive integer, default 1; invalid values are rejected at configuration validation). As `analyze` processes each candidate file it records the current recipe together with the verbatim spec of its referenced tool into the `recipe_snapshots` table: the snapshot document is `{"recipe": <the recipe's raw mapping>, "tool": <the referenced tool spec's raw mapping>}`, content-addressed by the SHA-256 of its canonicalized JSON and deduplicated by `UNIQUE(recipe_name, recipe_version, recipe_sha256)` — so edits to the tool definition also produce a new snapshot, and cache hits record a snapshot of the current configuration as well. `analysis_jobs.recipe_snapshot_id` points back to the exact configuration that produced the job; jobs adopted during resume inherit the original job's snapshot id (they were produced by that configuration, not today's). Inspect them with `operon recipes list / history / show`; the QC-profile counterparts recorded in `qc_profiles` are inspected with `operon profiles history / show`. Restoration via the CLI is print-only in both cases: a human copies the output back into the configuration YAML, and the CLI never rewrites files in place. The audited alternative is the TUI Config screen, whose structured editors save every change as the next version with a new snapshot and can restore any recorded snapshot into the editor (saving it creates the next version); TUI recipe saves normalize `tools.yaml` formatting and drop hand-written comments. <!-- version-pin -->

Run resource-usage recording (schema 2.9): `workflow_runs` gains `duration_seconds` (wall clock; previously only present in the JSONL), `avg_rss_mb` (average RSS), and `cpu_seconds` (core-seconds), and the pre-existing `max_rss_mb` column is now actually populated. Collection is per backend: <!-- version-pin -->

- `local`: a sampling thread polls `VmRSS` in `/proc/<pid>/status` when procfs is available and otherwise uses the POSIX `ps` RSS field (including on macOS) for peak and average; core-seconds come from the `getrusage(RUSAGE_CHILDREN)` delta across the run;
- `slurm`: after the job finishes, `sacct` is queried with extended fields (`MaxRSS`/`AveRSS`/`Elapsed`/`TotalCPU`); remote Slurm (`ssh` with `scheduler: slurm`) follows the same path;
- `ssh` direct: a remote POSIX sampling loop sums RSS for the isolated process group and writes a stats file that is read back (in direct mode `cpu_seconds` is left empty).

Whenever a backend cannot collect a metric the column stays NULL — no error is raised and the task itself is never affected; resource data serves auditing and capacity evaluation only and plays no part in the success verdict.

`run-external` provenance is aligned with `analyze`: `--tool NAME` matching a tool configured in `config/tools.yaml` triggers automatic version detection recorded as `tool_version` and `tool_version_raw` (a failed probe degrades to a warning and does not block the run); `--input PATH` (repeatable) declares input files whose per-file SHA-256 values are combined into `input_sha256`, with the full list recorded in `execution_details`; `--threads` records the thread count requested from the execution backend.

Graceful shutdown (`shutdown.py`): while an `analyze` batch is running, SIGINT/SIGTERM handlers are installed; a signal is converted into `ShutdownRequested` (a `KeyboardInterrupt` subclass) raised on the main thread, and cleanup follows the normal exception path — `local` backend subprocesses start with `start_new_session` in their own process group, and on interruption/timeout the whole process group (including grandchildren) receives TERM then KILL; the `slurm` and remote-Slurm backends `scancel` the current job on interruption; the `ssh` direct backend reuses the timeout path's remote process-group TERM/KILL. The current `analysis_jobs` row is set to `interrupted` (it does not participate in completed-cache hits), half-finished output is deleted by default (`--keep-partial` keeps it), and the batch then terminates with exit code 130; a second signal during cleanup forces an immediate exit. A `RUNNING` row left behind by a SIGKILLed process is swept to `interrupted` at the next `analyze` startup, so resume semantics always hold.

# Implicit Behaviors, Edge Cases, and Known Issues

This page corresponds to `operon` {{ operon_version }} (database schema {{ db_schema }}, metadata schema {{ metadata_schema }}). It documents behavior that is observable in the code but not stated on the task- or architecture-facing pages: implicit semantics, edge cases, and known issues. Items are described as they behave today, with the implementing module named so you can verify each claim. Nothing on this page is a usage recommendation; for the supported workflows see the [guides](../guides/index.md) and [troubleshooting](../guides/troubleshooting.md).

Historical known issues that have been resolved are listed first. The remaining
items describe current behavior and accepted limitations.

Each current item is classified:

- **Intended but implicit** — deliberate design whose consequences can still surprise (for example, what a state transition does to audit rows).
- **Limitation** — a capability boundary or robustness gap that is accepted for now.
- **Known issue** — a defect or data-semantics surprise reported here instead of being silently left undocumented. Any unresolved issue lists a workaround where one exists.

A bullet whose lead-in starts with **Known issue** is in the third class; the
remaining bullets are intended-but-implicit semantics or accepted limitations.

## Resolved issues

The following issues were previously reported against this page and are now
covered by the current implementation and regression tests:

| # | Area | Resolution |
|---|---|---|
| K1 | Decisions | Re-evaluation appends an automatic row while carrying the current `curated_*` fields forward. The CLI previews all affected curated entities and asks once before any write; non-interactive runs require `--yes`. |
| K2 | QC state | Each file has an aggregate QC status. An entity takes the worst sibling status (`QC_FAILED` > `QC_RUNNING` > `QC_COMPLETE`), and `operon qc` lists every file status. |
| K3 | Standardize | Batch standardization returns exit code 1 when any file fails. |
| K4 | Release | Releases are built in a hidden staging directory and published atomically. Failed builds remove staging output; a database commit failure also removes the published tree. |
| K5 | Release | Release membership, audited `RELEASED` transitions, and the release row commit in one transaction, so a partial state update is rolled back. |
| K6 | Export | Exports are built in a temporary sibling and renamed only after all artifacts are complete; failures clean the temporary tree or restore an existing empty destination. |
| K7 | Table import | Updating existing metadata preserves its lifecycle state and audit history. Release preflight treats changes after evaluation as stale and requires a fresh QC/evaluation. |
| K8 | Ingest (`move`) | Move mode copies and verifies the archive, registers it, and removes the source last. Copy, checksum, or transaction failures leave the source recoverable. |
| K9 | Utilities | Empty tables render one header and separator, without a duplicate data row. |
| K10 | Import wizard | The annotation prompt defaults to the draft's current presence (`yes` only when an annotation is already selected). |

## Identity, archiving, and the filesystem

- **Raw immutability is absolute, even after local loss.** Re-ingesting different bytes for the same entity + role raises `ConflictError` even when the previously archived file is missing or corrupted locally (`files.py`, ingest). There is no in-place replacement path; archive a new entity version or use an audited repair flow.
- **Untracked leftovers are quarantined, not deleted.** When the canonical target path inside `raw/` is occupied by bytes the manifest does not know, the occupant is moved to `<name>.orphan-<sha12-prefix>` in the same directory (`files.py`). Such files can appear inside the otherwise immutable archive and they are not manifest members; the claiming-row and audit details are on the [ingest page](cli-files-qc.md#ingest).
- **Compression detection is asymmetric.** A file *named* `.gz` whose magic bytes are not gzip is rejected, but a plain-named file whose content is gzip is silently recorded as `compression=gzip` (`files.py`, `detect_compression`).
- **Format detection reads extensions, then the caller's role, never content.** At most one `.gz`-style suffix is stripped, and the role fallback runs only after the extension lookup and before `other`, so `x.fasta.bz2` ingested as `genome_fasta` is recorded as `fasta` rather than `other` (`files.py`, `detect_format`).
- **Manifest relative paths are POSIX paths.** On Windows, `Project.project_rel` returns `os.path.relpath` verbatim, so a stored manifest path can contain backslashes; `remotes.py` is the only module that normalizes `\` to `/`, while release and export copy `relative_path` unchanged, so the storage contract is POSIX-only (`config.py`, `remotes.py`, `export.py`).
- **`standardize --link hardlink` falls back to a copy for directory artifacts** — only single files can be hardlinked (`files.py`, `standardize_file`). New standardized targets are published atomically and removed on any failure.
- **`verify` always computes full SHA-256; `qc` uses the stat-fingerprint cache.** A `touch` or copy invalidates the cache and forces a rehash in QC, but `operon verify` never consults the cache (`files.py`, `verify_local_file_identity` vs `verify_files`).
- **`REMOTE_UNVERIFIED` is an output-only status.** It is never persisted, writes no audit row, and leaves the existing `files.status` untouched — yet it alone drives exit code 1, so a network hiccup fails the command without being misclassified as data loss (see [verify](cli-files-qc.md#verify)) (`files.py`).
- **`verify` only live-checks remotes for files whose local bytes are absent.** When local bytes exist, remote drift is not detected (`files.py`).
- **`operon` commands run against the nearest enclosing project.** `Project.find` walks up parent directories looking for `project.yaml`, so a command in a subdirectory silently operates on the enclosing project (`config.py`).
- **Directory identity excludes timestamps and ownership.** `sha256_directory` covers relative paths, empty directories, file bytes, sizes, and symlink targets; a FIFO/socket inside a directory makes ingest/verify of that tree fail with `OSError` (`utils.py`).
- **Interrupted copies leave hidden temporary entries.** `atomic_copytree` works in a sibling `.target.XXXX` temporary directory, and `atomic_copy`/`atomic_write_text` leave sibling `.<name>.XXXX` temporary files; only an in-process exception removes them, so a SIGKILL or power loss leaves them for manual cleanup (`utils.py`).
- **Known issue: an idempotent re-ingest demotes `STANDARDIZED` to `CHECKSUM_VERIFIED`.** Re-ingesting identical bytes rewrites `files.status` unconditionally and writes no `changes` row, so a standardized file silently loses that status; `set_file_status` itself is a no-op that writes nothing when the status is unchanged (`files.py`, `database.py`).
- **Known issue: `standardize` bypasses the state machine and the audit log.** It writes the entity state `STANDARDIZED` directly, so standardizing a `RELEASED` or `ACCEPTED` entity — or running `standardize_all`, which selects on `files.status` alone — changes the entity state with no transition check and no `changes` row (`files.py`, `database.py`).
- **`standardize` re-hashes on every run.** Source and target hashes are recomputed each time and the stat-fingerprint cache is written but never read, so repeating the command costs a full pass over the bytes unlike `qc` (`files.py`).

## Database, transactions, and concurrency

- **Concurrent writers are serialized only up to 30 seconds.** The database runs in WAL mode with `busy_timeout=30000` and immediate write transactions; writers wait for the lock before reading and a writer that exceeds the timeout still fails with `database is locked` (exit 1). Stable IDs are reserved under the same lock, so concurrent allocations are unique; failed inserts can leave gaps (`database.py`).
- **Migrations run on every writable open, not only on `operon migrate`.** Opening a project with an older schema applies pending additive migrations as a side effect of any command (`database.py`). Migrations are additive (new columns/tables); there is no destructive migration and no data backfill, except the pre-1.0 rebuilds (see [database compatibility](../operations/database-compatibility.md)).
- **Read-only access requires an empty WAL.** A read-only mount can only be opened when the `-wal` file is empty; otherwise the open fails with instructions to checkpoint on a writable host (`database.py`).
- **`operon query` rejects more than table writes.** The SQL authorizer denies DML/DDL/ATTACH/SAVEPOINT and allows only a whitelist of read-only PRAGMAs, so side-effecting statements that are not table writes fail too: `PRAGMA journal_mode` reports *not authorized* and `VACUUM` reports *authorization denied* (see [query](cli-decisions-reports.md#query)) (`database.py`).
- **Setting the current state is only half a no-op.** The audit row is written only when the state actually changes, but the `entity_state` row is rewritten unconditionally: an equal-state call still replaces `message` (a `None` message clears it) and `updated_at` while writing no `changes` row. `set_state_bulk` forces every transition — bypassing the transition table — but keeps the same conditional audit behavior (`workflow.py`, `database.py`).
- **Known issue: re-running `qc` demotes `ACCEPTED`/`RELEASED` entities.** QC drives its state writes through the forced bulk path and offers no `--force` or prior-state warning, so an accepted or released entity drops to `QC_RUNNING` and then `QC_COMPLETE`/`QC_FAILED`; `evaluate` does the same for an entity without a `curated_decision`, while a curated decision is protected and curated re-evaluation warns before writing (`qc/__init__.py`, `rules.py`, `cli.py`).
- **Known issue: concurrent writable opens can collide while rebuilding views.** Every writable open drops and recreates `current_decisions`, `effective_retired_entities` and `current_entity_lifecycle` without a lock or a transaction, so two `operon` processes (or the CLI and the TUI) can abort with `sqlite3.OperationalError: view current_decisions already exists` — a logical conflict the 30-second busy timeout cannot absorb, surfacing as exit 1 (`database.py`).
- **Every writable open rebuilds schema objects.** The view rebuild changes `PRAGMA schema_version` and writes to the WAL on each writable open even when no data changes; read-only commands return before any of it (`database.py`).
- **A database from a newer schema is accepted silently.** Nothing reads or compares the stored `database/SCHEMA` marker, and `SCHEMA_VERSION` is only written and reported: an older binary opens the database, re-stamps the marker with its own version string and recreates its views (`database.py`, `cli.py`).
- **`project.yaml` is not validated and `init` is not atomic.** A missing or renamed key raises a bare `KeyError` (traceback, exit 1) instead of a configuration error; `Project.init` writes `project.yaml` first, so a later failure leaves a half-initialized project that `Project.find` accepts while a retry refuses to re-initialize it (`config.py`, `cli.py`).
- **Three default configuration keys have no reader.** `resources.max_memory_gb`, `qc.sample_reads_for_duplicates`, and `project.description` are written by `operon init` and read by no code path (only `resources.default_threads` and `qc.default_profile` are consumed), so setting them has no effect and produces no warning (`config.py`, `tools.py`).

## Timestamps, logs, and ordering

- **Timestamps are local time with offset, not UTC — and one database mixes both.** `now_iso()` emits e.g. `2026-09-05T14:30:00+08:00`, and most timestamp-ordered logic compares these strings lexicographically, which is only safe because all writers share the same clock/offset; `julianday()` compensation exists in `workflow list`, in release staleness checks and in the TUI, while the `database/SCHEMA` marker and `schema_migrations.applied_at` are written with SQL `datetime('now')` (UTC, space-separated) in the same database (`utils.py`, `workflow.py`, `release.py`, `database.py`).
- **`logs/workflow.jsonl` and the database can disagree.** JSONL run records are appended without inter-process locking and flushed after the DB commit, and a rolled-back transaction discards its buffered records; each record is written with one append plus `fsync`, so the realistic risk is a missing, duplicated or out-of-order line rather than a torn one (`utils.py`, `workflow.py`).
- **Run input identity embeds absolute paths.** `workflow_runs.input_sha256` hashes the list of `path:sha256` lines; the same content at a different path (moved project) yields a different input identity (`workflow.py`).
- **Run input identities are not comparable across steps.** External commands hash a `path:sha256` list while built-in QC stores the plain file SHA-256, so the same file has a different `input_sha256` per step; `log_run` also defaults `tool_version` to the `operon` version, so ingestion and QC rows report Operon itself as the tool (`workflow.py`, `qc/__init__.py`).
- **Output limits are implicit.** `workflow list` defaults to 50 rows (`--limit 0` = unlimited, `--to` is exclusive; see [workflow list](cli-workflow.md)) and `report analysis` to 20 rows with no truncation hint, while `report qc` and `report decisions` are unbounded; empty results print literal sentinels such as `(no QC results)`, `(no decisions)` and `(no analysis results)` (`cli.py`, `reports.py`).
- **Failure bookkeeping is best-effort.** Where a failure or interrupt path writes its own `workflow_runs` row inside a `try`/`except Exception: pass` and then re-raises the original error, a failing bookkeeping write is swallowed, so a failed command can leave the run row `running` with no trace of the bookkeeping failure (`import_wizard.py`, `taxonomy.py`, `adapters/ncbi_datasets.py`).
- **Executor environment probes fail silently.** If environment capture fails, the run completes with no `environment_id` and no warning (`workflow.py`).

## Metrics and decisions

- **Formats without a parser stay `QC_COMPLETE`.** A required rule whose metric has no value evaluates to `NOT_EVALUATED` instead of failing (see the [QC profiles guide](../guides/qc-profiles.md)), so formats with no parser (for example BAM) also stay `QC_COMPLETE` and are excluded from releases only by never reaching `PASS` (`rules.py`).
- **`evaluate` only sees entities that have QC results.** Entities never processed by `qc` receive no decision; release preflight now rejects such active in-scope entities before creating output (`rules.py`, `release.py`).
- **Multi-file entities mix metrics from different files.** `latest_metrics` partitions by input identity: conservative booleans (`file_exists`, `sha256_match`, `parseable`, `paired_read_count_match`) take the minimum across all inputs, but every other metric takes the most recently evaluated input's value — a decision can combine counts from one file with booleans from another (`database.py`).
- **Changing QC sampling parameters accumulates rows.** QC results upsert on the parameter set; re-running `qc` with a different `--sample-size`/`--phred-offset` adds a parallel set of rows rather than replacing, and the newest silently wins in `latest_metrics` (`database.py`).
- **Threshold semantics are inclusive and string-based for sets.** `>=`/`<=` are inclusive, `between` is inclusive on both ends, `in`/`not_in` compare metric values as strings, and a rule without `operator` always passes (`rules.py`). Profile-shape gaps (missing `min`/`max`/`values`) behave as described in the [QC profiles guide](../guides/qc-profiles.md).
- **`curate` accepts any decision string.** Values are uppercased but not validated against the decision enum; an unrecognized value stores verbatim and maps the entity to `QC_COMPLETE` (`rules.py`).
- **A broken profile only affects the profile it names.** `evaluate` loads the single named profile file and `analyze` does not read profiles at all, so neither enumerates `config/profiles/`; a scratch or half-edited YAML there is harmless unless it shadows the named profile, and the directory-wide listing belongs to the TUI profile screen (`rules.py`, `profiles.py`). When the named profile does have a YAML syntax error the command fails with a traceback and exit 1 rather than an `error:` message, because `yaml.YAMLError` is not an `OperonError` (`cli.py`).
- **Manual overrides survive re-evaluation.** The newest automatic decision carries forward the current `curated_*` fields; use `curate` for an explicit lifecycle change (`rules.py`, `cli.py`).
- **Numeric rules applied to text metrics fail late.** `latest_metrics` can return a text value, and a numeric operator then raises a bare `ValueError` that the CLI prints as a context-free `error: ...` with exit 1 instead of a validation error naming the rule or metric (`database.py`, `rules.py`, `cli.py`).

## Built-in QC parsing

- **Whitespace inside FASTA sequence lines is counted as invalid bases.** Lines are stripped at the ends but interior spaces remain and inflate `invalid_base_count`; sequence data must be ASCII (`qc/parsers.py`).
- **The seqid is the first whitespace token of the header.** Duplicate detection separately counts full headers and seqids (`qc/parsers.py`).
- **Protein internal-stop counting forgives a terminal `*`.** A trailing stop codon is subtracted (clamped at 0); `missing_start` requires the first residue to be `M` (`qc/parsers.py`).
- **FASTQ duplication is measured on the first N reads only.** `duplicate_sampling_strategy=first_n` with the default sample of 1,000,000 reads; duplicates clustered late in a much larger file are invisible (`qc/parsers.py`).
- **Phred `auto` assumes 33 when ranges overlap.** Overlapping Sanger/Illumina quality ranges are resolved silently; the uncertainty is only visible via `quality_encoding=ambiguous_assumed_phred33`. Quality characters outside ASCII 33–126 abort QC (`qc/parsers.py`).
- **GFF3 tolerates several irregularities.** Rows with ≠9 tab-separated fields count as `coordinate_error_count` and are skipped; content after `##FASTA` is ignored; the CDS multiple-of-3 check uses coordinates only and ignores the phase column; Parent integrity is checked against the whole file, so forward references pass (`qc/parsers.py`).
- **`parseable` exists only for formats with a parser.** FASTA/FASTQ/GFF3 record it; other formats leave the `parseable == 1` gates permanently `NOT_EVALUATED` (`qc/__init__.py`).
- **Paired-read matching is silently skipped** when the sibling FASTQ has no manifest row or is not on disk — no metric and no warning (`qc/__init__.py`).
- **A corrupt FASTA-length cache is silently rebuilt.** Digest/count mismatch deletes and regenerates the cache (`qc/__init__.py`).
- **Cython and pure-Python parsers have zero tolerated differences.** Metrics and error message strings must match byte-identically; this is enforced by `tests/regression/test_cython_parser_parity.py`.
- **Known issue: a directory artifact can never pass built-in QC.** `verify_local_file_identity` requires a regular file, so QC records `file_exists=0` and marks the file and its entity `QC_FAILED` with "file missing or checksum mismatch", while `verify` hashes the directory tree and reports `CHECKSUM_VERIFIED` for the same artifact (`files.py`, `qc/__init__.py`).
- **`qc --file-id` still inherits sibling failures.** Because the entity status aggregates every sibling file, a targeted run of one healthy file exits 1 while a sibling is `QC_FAILED`; a `--file-id` run naming a `REMOTE_ONLY` file exits 1 because the only result was skipped (`qc/__init__.py`, `cli.py`).
- **R1/R2 pairing trusts unverified sibling bytes.** The sibling FASTQ is counted by re-reading it, with no manifest checksum check, so corruption that preserves the record count leaves both the pairing metric and the reported integrity intact (`qc/__init__.py`, `qc/parsers.py`).
- **An annotation inherits its sibling's failure.** Assembly and protein inputs are verified before the GFF3 is parsed, so a missing or changed sibling records `parseable=0` on the annotation and fails it (`qc/__init__.py`).
- **Duplicate seqids inflate lengths and weaken GFF3 coordinate checks.** The length map sums every record carrying the same seqid, so an assembly with duplicate seqids reports inflated totals and a feature end beyond the real record length can still pass the coordinate check (`qc/parsers.py`, `qc/__init__.py`).
- **Read over-representation uses a hard-coded threshold.** A sequence counts as over-represented above more than 1 % of the first-N sampled reads — a threshold inside QC code rather than in a versioned profile, and one that inherits the sampling blind spot (`qc/parsers.py`, `qc/_parsers.pyx`).
- **`protein_stats` penalizes only `X` and `*`.** Every other residue is accepted and counted, so `-`, `J`, `O`, `U` and digits are neither penalized nor reported, and the defined protein-alphabet constant is never referenced (`qc/parsers.py`).
- **Alignment QC uses its own median and collapses headers.** Even counts take the upper median and consensus ties go to the first-seen residue (unlike `utils.median`), and `safe_id` is the first whitespace token of the header, so headers that differ later collapse into one row with no duplicate detection (`qc/alignment.py`, `qc/parsers.py`).
- **`qc-measure` mixes parameter sets.** `file_exists` is written under the default parameter set while the other stages use the caller's set, and GFF3 measurement needs at least one of `--assembly-fasta`/`--protein-fasta`; a custom-parameter-set measurement therefore imports one row that lands in the default set, where a later local QC can overwrite it (`qc/measure.py`, `qc/__init__.py`).
- **Unmeasurable values become real zeros.** `pct(x, 0)` and `median([])` return `0.0`, so an empty FASTA stores `gc_percent=0` and `median_sequence_length=0`, which rules then compare as measurements instead of `NOT_EVALUATED` (`utils.py`, `qc/parsers.py`).
- **`qc_all` silently skips superseded and retired entities.** A batch run can report success while whole entities were never processed, including an explicit `--entity-id` that names a superseded entity (`qc/__init__.py`).

## External analyses

- **Reference-database identity depends on the database mode.** Without an explicit `database_checksum`, a single-file database is hashed by full content, a directory database is fingerprinted only by each file's relative path, size and mtime, and `database_mode: mutable_cache` ignores content entirely; directory databases (BLAST index directories) therefore produce spurious cache misses on a touch or copy and can reuse stale results after an in-place edit that preserves size and mtime, and their individual index files never acquire an identity of their own (`tools.py`).
- **Tool-version probing has a coarse fallback.** If the version regex misses, the first version-looking token — or the entire first output line truncated to 200 characters — becomes `tool_version`; raw probe output is truncated to 4000 characters in provenance (`tools.py`).
- **BLAST tabular parsing drops silently.** Lines whose field count differs from `result_columns` are skipped without error, and `max_hits_per_query` (default 5) truncates stored hits per query — `analysis_results` summaries can under-count (`tools.py`).
- **Result parsing is not atomic.** Hits and results are written in separate transactions; a crash mid-parse leaves partial hits for a job that is then marked failed (`tools.py`).
- **Empty tool output is a failure.** A run is `completed` only when the exit code is 0 and every expected output exists and is non-empty; a legitimately empty 0-byte TSV fails the run (`workflow.py`).
- **BUSCO auto-lineage rejects paths containing `fasta`.** This is a deliberate guard against the SEPP path-rewriting bug; see the [recipe examples](recipe-parsers-examples.md) (`tools.py`).
- **Stale cache entries self-heal.** A cached job whose output was deleted or modified is marked `superseded` and re-run; leftover stale output is removed first (`tools.py`).
- **Dry runs against non-local backends cannot probe versions.** They use a placeholder tool version, so the printed cache verdict may differ from a real run (`tools.py`).
- **`analyze --limit N` takes the first N files in `file_id` order** — a batch-size control, not a fairness guarantee (`tools.py`).
- **Interrupted external commands leave no run row.** `run-external`/`analyze` log their `workflow_runs` row at the end; a `KeyboardInterrupt`/`ShutdownRequested` mid-run leaves only stdout/stderr logs and (for analyses) an `interrupted` `analysis_jobs` row (`workflow.py`).
- **`--threads` participates in the cache fingerprint.** The resolved thread count (default 4) is hashed into the parameter fingerprint, so changing it re-runs every file even when the tool's output would be identical (`tools.py`).
- **`analyze` passes no timeout to any backend.** A hung tool therefore runs indefinitely locally and over SSH, and the Slurm backends are bounded only by the default `--time=24:00:00` (`tools.py`, `execution.py`).
- **Known issue: a failed run keeps its partial output.** Only an interrupt removes the computed artifact; any other failure, including a result-parsing error, leaves the truncated TSV or half-written output directory on disk as if it were a result (`tools.py`).
- **`analyze` can rewrite the manifest.** With an SSH `storage_remote`, a file whose local bytes are absent and whose remote copy verifies is silently re-marked `REMOTE_ONLY` with an audit row, so an analysis mutates file status (`tools.py`).
- **Known issue: the stale-`RUNNING` sweep has no ownership filter.** Every non-dry `analyze` marks all `RUNNING` analysis jobs `interrupted`, so two concurrent analyses can interrupt each other's live jobs (`tools.py`).
- **Result summaries are computed from the capped hit set.** `hit_count`, `best_evalue` and the derived "top hit" use only hits kept under `max_hits_per_query`, and `hit_rank` is the line's position in the result file rather than a score ranking, so summaries can under-count and mis-order (`tools.py`).
- **Recipe typos degrade silently or raise a bare error.** A metric column absent from `result_columns` is dropped without a message, while a query or subject column that is not in `result_columns` raises a plain `ValueError` (exit 1, not a validation error) (`tools.py`).
- **HMMER parsing has asymmetric defaults.** Without a `# <program> ::` header the hmmscan column mapping is assumed, and the tblout parser silently drops lines with fewer than six fields where the rpsbproc parser raises (`tools.py`).
- **Version and database identities are cached for the process lifetime.** Module-level dictionaries are never invalidated, so a long-lived process (for example the TUI) keeps stale tool versions and database fingerprints after a tool or database changes (`tools.py`).
- **Version probing is bounded and staged under `logs/`.** It uses a hard-coded 120-second timeout and stages its temporary output in the project's `logs/` directory; neither is configurable (`tools.py`).
- **A command chain validates only the final step's outputs.** Intermediate outputs are never checked before the run is recorded `completed`, so a chain can be "completed" with a missing intermediate artifact (`workflow.py`).
- **Adopted lineage edges are insert-only.** `INSERT OR IGNORE` on `(derived_file_id, input_file_id)` means re-adopting never updates `workflow_run_id` and there is no update path at all (different bytes raise `ConflictError`); the first absolute source path wins as `source_url`, relative manifest paths resolve against the project root rather than the working directory, and no self-reference or cycle check exists (`lineage.py`).
- **`extract-domains`/`select-sequences` read every completed job.** Alignments come from all completed jobs for the file with no latest-job selection, and the source FASTA is never checksum-verified (`sequence_tools.py`).
- **Sequence extraction copies bytes verbatim.** Sub-sequences keep gaps and ambiguity codes, `--min-length` is applied before flanks are added, and order and names are lexical (`seq10` before `seq2`) with flanked coordinates in `--all-regions` headers; a non-positive start in a `--regions-tsv` table is rejected while database-derived coordinates are clamped to 1 (`sequence_tools.py`).
- **Empty or repeated extractions are quiet.** An empty result is a 0-byte FASTA with exit 0 and reasons only in the optional manifest, existing outputs are silently overwritten and never registered, a non-empty `sequences` registry replaces the FASTA-derived seqid universe (although the FASTA is still parsed for sequence bodies), and a duplicate seqid keeps the first record (`sequence_tools.py`).
- **Classification labels are keyed by profile name and re-audited on any metric change.** `sequence_labels` is unique on `(file_id, seqid, profile_name)`, so a profile version bump overwrites labels in place, and `details_json` embeds the observed hit, so a changed metric re-audits every label even when the label is unchanged; deletions are limited to files in the current scope, so out-of-scope stale labels persist (`classify.py`, `database.py`).
- **Known issue: `not:` matches a missing field.** A negated condition is satisfied when the field is absent, contradicting the module docstring's rule that a missing field never satisfies a condition; `between` also bypasses the numeric guard and raises a plain `ValueError`, while `in`/`not_in` compare `str(value)` (`classify.py`).
- **Classification silently ignores what it cannot see.** Only the single highest-`job_id` completed job per analysis and file contributes, and files absent from the `sequences` registry are skipped and merely counted (`classify.py`).
- **`fanout --dry-run` skips real preflight, and unit bytes depend on TSV row order.** The dry run returns before checksum verification and conflict/occupancy checks, so it can print units a real run rejects, and reordering the assignment TSV changes the unit bytes and triggers `ConflictError`; unit roles `<prefix>:<unit>` put `:` into the archive filename, and the downstream `file_role_prefix` selection is a literal string prefix, so `sub` also captures `sub2:*` (`fanout.py`, `tools.py`).
- **`fanout` leaves a `running` run row on Ctrl+C.** Created targets are removed but `finish_run` is skipped, so the workflow run stays `running`; zero units and unresolved or ambiguous seqids are hard errors. Source SHA-256 and registry freshness are verified for `--source-file` FASTAs, but the assignments table itself is not checksum-verified (`fanout.py`).

### TimeTree

- **TimeTree query caching is permanent and opaque.** The cache is keyed by URL with no TTL, `--refresh` overwrites the single record, and a corrupt record is a permanent hard failure with no network fallback; `--retries` (1–10, default 3) counts total attempts with no `Retry-After` handling, errors truncate the body to 500 characters, and every successful real request is followed by a fixed delay (`adapters/timetree.py`).
- **`timetree fetch` uses a fixed inter-request delay.** The 1.0-second delay is hard-coded and not exposed as a flag; snapshot publication refuses to overwrite and a single invalid pair aborts the whole run; `load_snapshot` re-verifies every raw response but never re-checks the recorded `pairs_sha256`; `calibrations --out` overwrites its target non-atomically; and the query subcommands require a project and write a `workflow_runs` row even on a cache hit (`timetree.py`).
- **Calibration summaries are heuristic.** Nested objects are flattened and the first record carrying any of about six age-key aliases wins; `timeline` parses any response body as CSV without a format check; and calibration rows embed the absolute local cache path and the original retrieval time (`adapters/timetree.py`).
- **Known issue: TimeTree inputs fail with bare exceptions.** Constraint `taxon_a`/`taxon_b` coerce with an unguarded `int()` (exit 1 with a context-free message) where the sibling pairs table raises a `ValidationError` (exit 2); a snapshot without a `records` key raises a bare `KeyError` traceback, and a snapshot whose raw response file was deleted fails as an `OSError` (exit 1) instead of the documented validation error (`timetree.py`).

## Execution backends

- **Local CPU time can over-count.** `cpu_seconds` is a delta of `getrusage(RUSAGE_CHILDREN)`, which includes any other children reaped concurrently by the same process; Windows has no `resource` module, so `cpu_seconds` is `None` there (`execution.py`).
- **The Slurm payload runs only if `cd` succeeds.** The generated batch script guards the payload with the `cd` exit code and always writes the exit-code file (`execution.py`).
- **`sacct` memory parsing treats bare numbers as bytes.** Slurm prints small exact values without suffixes, so `MaxRSS=123` is parsed as a tiny MB value (`execution.py`).
- **SSH timeouts may leave the remote process running.** The payload runs under `setsid --wait` with a `/tmp` pidfile; on timeout the process group receives SIGTERM then SIGKILL, but a missing pidfile means the error can only warn that the remote process may still be running (`execution.py`).
- **Output pull is asymmetric.** A remote output that does not exist is skipped (the expected-output check reports it), but a local output with different content raises `ConflictError` (`execution.py`).
- **Path rewriting follows the resolved path.** Remote execution rewrites an argument whose resolved target is inside the project root even when the literal argument is not, and a path that is lexically inside but resolves outside raises `ValidationError` (`execution.py`).
- **Every local command runs an environment probe first.** `LocalExecutor.run` always executes a shell probe with up to 30 seconds of timeout before the payload, so even a single run pays that cost (`execution.py`, `environment_capture.py`).
- **Resource sampling watches only the direct child.** With the default `conda run`/`mamba run` launcher, `max_rss_mb`/`avg_rss_mb` describe the launcher process rather than the tool it starts (`execution.py`).
- **A failed environment capture is stored as the run's environment.** The placeholder `{"capture_schema": 1, "capture_status": "failed"}` document becomes the job's environment, and a later `strict` comparison sees `unavailable` and degrades to `warn` (`execution.py`, `workflow.py`).
- **Slurm cancellation failures are silent locally.** The local Slurm backend ignores `scancel` failures on timeout and on interrupt, while the remote-Slurm path records `cancellation_error` and warns; a mid-poll `squeue`/SSH control failure aborts without any `scancel`, so a running job can be orphaned (`execution.py`).
- **Known issue: an OOM-killed Slurm job can be recorded as success.** Exit-code and accounting retries are fixed at 5 attempts × 1 s, and the `sacct` fallback keeps only the first component of `exit:signal`, so an OOM kill reported as `0:9` becomes exit code 0 (`execution.py`).
- **Slurm defaults are permissive.** `--time=24:00:00`, no partition and no memory unless configured, and a 15-second `poll_interval` whose effective minimum is 0.1 s (`execution.py`).
- **`setup_commands` run before the job changes directory.** They execute ahead of the payload's `cd`, so relative paths in them behave differently from the payload's (`execution.py`).
- **Known issue: the SSH backend deletes remote outputs before every run and pulls only on success.** A failed run destroys the previous remote output, and `--keep-partial` cannot help because nothing is pulled back (`execution.py`).

## Remote mirrors

- **A stale manifest lock blocks all locked operations until removed by hand.** The lock is an atomic remote `mkdir` with no expiry; a crashed push deliberately leaves `.operon-manifest.lock` behind, and the error message names the exact path (`remotes.py`).
- **A failed manifest publication leaves unindexed remote files.** If per-file uploads succeeded but the final manifest write failed, remote objects stay on the server unindexed while the local batch reports error; the next push finds the identical bytes and records them as `indexed` (`remotes.py`).
- **A remote manifest without a `project_id` is silently adopted.** Pointing a remote at an empty or unmanaged directory claims it without confirmation (`remotes.py`).
- **`pull` without `--file-id` requires the entries to exist locally.** It iterates the remote manifest and raises `ConflictError` for any entry absent from the local database; remotes are mirrors of an existing manifest, not standalone restores into an empty project (`remotes.py`).
- **Eviction checks one named remote.** `evict` sets `REMOTE_ONLY` based on a single remote; other configured remotes may lack the file, and `verify` accepts any single verified remote as sufficient (`remotes.py`, `files.py`).
- **`sftp://` ingest has no integrity anchor.** There is no expected-hash or host-key pinning option; correctness relies on the ingest-time hashing of the received bytes (`remotes.py`).
- **Directory artifacts stream the whole tree per check.** `matches()` on a directory walks every file over SFTP, so push/pull/evict of directory artifacts costs O(tree size) per check (`remotes.py`).
- **Only `push` takes the manifest lock.** `push` is the sole `manifest_lock()` caller; `pull`, `evict` and `check_remote` never wait for it, and for `push` the wait is bounded by the per-remote `connect_timeout` (default 30 s) (`remotes.py`).
- **A lock-release failure after a successful publish reports failure.** The new manifest is already published inside the lock, so a push can report exit 2 while the remote holds the new objects (`remotes.py`).
- **`connect_timeout` bounds only the SSH handshake.** SFTP put/get/stream operations and the lock's own SFTP calls have no timeout, so a hung transfer never aborts (`remotes.py`).
- **Remote hashing is bounded and then falls back to streaming.** `sha256sum` gets a hard-coded 600-second timeout, after which the file is streamed in 1 MiB chunks over SFTP (`remotes.py`).
- **Replacing a remote manifest requires the server's POSIX rename.** Publishing an updated manifest uses the SFTP `posix_rename` extension; without it the second push can never publish (`remotes.py`).
- **A no-op push does not adopt the remote.** The remote manifest is written only when an entry changes, so an all-skipped push leaves it without a `project_id`, and `pull` never writes the remote manifest, so the adoption of an unmanaged remote is not durable (`remotes.py`).
- **Known issue: a failed upload verification poisons the remote path.** `put` publishes the uploaded bytes to the final path before `push` verifies them, so a truncated upload stays there with no manifest entry; the next push takes the "different bytes" path, marks the location `CORRUPT` and refuses to overwrite until an operator removes the object by hand (`remotes.py`).

## Releases and exports

- **Hashes cover less than the file names suggest.** `checksums.sha256` covers the data files only; `provenance.json` carries just a bare `metadata_sha256` for the metadata TSVs, `manifest.tsv` is hashed only into the DB summary and the `releases` row, and `qc_summary.tsv`, `decisions.tsv`, `profile_history.tsv`, `exclusions.tsv`, `software_versions.tsv` and `README.md` are hashed nowhere (`release.py`).
- **Release preflight requires decisions for every active in-scope entity.** Missing decisions, or metadata changed after evaluation, reject the release before any output is published, so those entities cannot silently disappear; exclusions are built from the profile's current decisions, so a retired entity that has no decision for that profile appears in neither `manifest.tsv` nor `exclusions.tsv` (`release.py`).
- **Known issue: release preflight is silently disabled when the profile file is missing.** The check returns early if `config/profiles/<profile>.yaml` does not exist, so `operon release --profile <typo>` publishes a zero-member release with exit 0 and `operon export --decision PASS --profile <typo>` writes an empty bundle (`release.py`).
- **Preflight and the QC snapshot are partial.** Preflight covers only entity types that have manifest files and only the five `_ENTITY_TABLES` types, so other entity types skip the stale-evaluation check, and `qc_summary.tsv` is neither profile-filtered nor hashed (`release.py`).
- **Known issue: a hardlink fallback is invisible in provenance.** A rejected `os.link` falls back to an ordinary copy silently while `provenance.json` still records `hardlink` (release) or `link_kind: hardlink` (export), and directories are always copied (`release.py`, `export.py`).
- **Known issue: the published tree and the database row are not atomic.** A crash between the final rename and the `releases` insert leaves a release directory with no row, and the retry then fails with `FileExistsError` until the tree is removed by hand (`release.py`).
- **Release and export output inherits staging permissions.** The staging directory is created with mode 0700 (and atomic single-file copies are created 0600) before being renamed into place, so a published tree can be unreadable to other users while sidecar TSVs keep the umask default (`release.py`, `export.py`, `utils.py`).
- **Selection errors are asymmetric.** An unknown `--file-id` silently selects nothing in `export` where `push`/`pull`/`evict` raise for the same input, a `--profile` given without `--decision` has no effect, and the export `manifest.tsv` omits the `compression` column that the release manifest carries (`export.py`, `remotes.py`).
- **Known issue: the export run row can claim a publication that never happened.** The `workflow_runs` row is committed before the final rename and its command embeds the staging path, so the database and JSONL can report a completed export whose destination does not exist (`export.py`).
- **Known issue: symlink export writes into an existing empty destination.** In that case the workspace *is* the caller's directory, and a failure path deletes every child of it (`export.py`).
- **An export selecting zero files succeeds.** Exit 0 with a header-only `manifest.tsv` (11 columns) and a 0-byte `checksums.sha256` that `sha256sum -c` refuses as containing no checksum lines (`export.py`, `schema.py`).
- **Export symlinks store fully resolved targets.** `--link symlink` points at `source.resolve()`; moving the project breaks the links, although checksum verification through them still works (`export.py`).
- **Release/export failures are recoverable.** Both commands stage output and clean it on errors, so an interrupted or failed run does not deliberately publish a partial destination; an OS-level crash can still leave a hidden staging directory for later housekeeping.
- **`--link hardlink` shares inodes with `raw/`.** Choosing hardlinks re-introduces inode sharing between the release and the raw archive, which the immutability reasoning assumes away; the default and its rationale are on the [release architecture page](../architecture/release-lifecycle.md) (`release.py`).

## Lifecycle and identity resolution

- **Retire is idempotent only for a direct retirement.** Retiring an entity that is already directly retired reports `changed: False`, but an entity retired only through an ancestor receives a new direct `RETIRE` and reports `changed: True` — it then survives a later ancestor restore. Restore is root-only: an entity that inherited retirement cannot be restored alone, and a direct child retirement survives a parent restore (`lifecycle.py`).
- **Retirement is purely logical.** `physical_changes` are hard-coded zeros: no metadata rows are deleted and no bytes are moved; the reference graph and the no-`purge` policy live on the [release architecture page](../architecture/release-lifecycle.md) (`lifecycle.py`).
- **`reason_code` is validated before the idempotency shortcut.** Re-retiring an already-retired entity with an unknown code raises instead of reporting `changed: false` (the CLI restricts the flag to the same seven codes, so this bites direct API callers); `restore` silently replaces any caller-supplied reason code with `manual_restore` (`lifecycle.py`).
- **Bare accessions are matched case-sensitively.** Internal IDs (`ASM_000001`) are case-insensitive and uppercased, but a bare accession must match its stored case; an accession mapping to several entities requires `NAMESPACE:ACCESSION` (`entity_view.py`).
- **`show` refuses retired entities by default.** It errors on a retired match unless `--include-retired` is given, and silently hides retired/superseded descendants otherwise (`entity_view.py`).

## Metadata, table import, and taxonomy

- **The literals "na", "n/a", "null", "none" become NULL.** In any string field, case-insensitively, unless the field's `allowed` list contains that exact token — a strain literally named "None" or isolate "NA" is silently dropped (`schema.py`).
- **Schema coercions are silent and not type-scoped.** The missing-value rule applies to every field type, so a numeric or date field literally containing `NA` becomes NULL; an unrecognized non-empty value in a boolean field becomes `1`; and duplicate TSV header names collapse in the parsed row with the last column winning (`schema.py`).
- **`id`-type fields are uppercased; `allowed` values are canonicalized.** Input is matched case-insensitively and stored in the schema's spelling (`schema.py`).
- **TSV comments are structural.** Any line whose first non-space character is `#` is skipped, including data rows; the header must be the first non-comment line; a ragged row is an error except for one missing trailing empty column when the header ends with an empty name. Files with a BOM are handled (`schema.py`).
- **Duplicate-key detection can be incomplete.** Once any earlier row in a table import produced a field error, duplicate-PK/unique checks are skipped for later rows in the same batch, so the failure list may be shorter than reality (`schema.py`).
- **Date validation follows the Python version.** `datetime.fromisoformat` on Python 3.11+ accepts loose formats such as `20240115`; on 3.10 the same value errors (`schema.py`).
- **XLSX reads only the first worksheet** in workbook order, whatever its name; other sheets are ignored. Excel serial dates with a fractional part become datetimes (`table_import.py`).
- **A blank cell clears an existing value on update.** The preview diff shows it, but omitted columns retain current values; `--on-conflict error` refuses to run if any row would change. The whole apply is one transaction (`table_import.py`).
- **Metadata patches preserve lifecycle state but invalidate evaluation freshness.** Updating an existing row records the field-level audit change; a later release preflight requires QC/evaluation after that timestamp (`table_import.py`, `release.py`).
- **Intra-file forward references are not resolvable.** Reference validation cannot resolve an ID that appears later in the same file; import organisms before samples before runs/assemblies, in separate runs (`table_import.py`).
- **Taxdump snapshots have no extinction data.** `is_extinct` is stored as NULL for taxdump imports, so a coverage profile with `exclude_extinct: true` fails loudly against them instead of weakening the rule; only NCBI Datasets JSONL sources carry the field (see the [taxonomy coverage guide](../guides/taxonomy-coverage.md)) (`taxonomy.py`).
- **A failed taxonomy import leaves the source copy on disk.** The source is copied into `raw/metadata/ncbi_taxonomy/` before the import transaction; on failure the transaction rolls back but the copied file remains unregistered (`taxonomy.py`).
- **Taxonomy versions are immutable.** Re-importing the same version with different bytes raises `ConflictError`; parent/alias referential integrity is enforced at import time, so incomplete taxdumps are rejected (`taxonomy.py`).
- **Coverage percentages are rounded before comparison.** Values are rounded half-up to 4 decimals before the inclusive `>=` threshold comparison, so 79.99996 % rounds to 80.0000 % and passes an 80 % threshold (`coverage.py`).
- **Coverage only supports NCBI taxonomy.** Observations with a taxonomy source other than `NCBI` are excluded as `UNSUPPORTED_TAXONOMY_SOURCE`, and a reused cached report whose decision is FAIL surfaces exit code 1 (see the [taxonomy coverage guide](../guides/taxonomy-coverage.md)) (`coverage.py`).
- **Reference sets are unpatchable.** Their identity is `{profile_name}@{taxonomy_version}` with no profile content version, so editing the profile and recompiling raises `ConflictError` instead of producing a new reference set (`taxonomy.py`).
- **Coverage reports embed a frozen profile and cannot be regenerated.** A report stores the compiled profile document and never re-reads `config/profiles/*.yaml`; there is no `--force`, so a deleted or tampered `COV_*` report directory leaves the CLI unable to rebuild it (`coverage.py`).
- **Coverage counts taxonomic breadth, not sampling depth.** The numerator counts a reference target once however many distinct organisms hit it, the metadata scope writes blank file/member evidence, retired organisms are dropped with no exclusion reason code, and report IDs are `COV_{input_sha[:16]}` (`coverage.py`).
- **Exclusion reasons are first-match-wins and deduplicated.** `excluded_observation_count` counts one row per (organism, reason) rather than one per observation, and the lineage walk stops below depth 100 (`coverage.py`).
- **Every coverage run re-verifies its reference set.** The reference TSV's SHA-256 and size are checked against the database row, the sidecar provenance, the frozen profile and the row counts, so re-syncing or editing a reference-set file makes all of its existing reports unusable even though the files are not deleted (`coverage.py`).
- **Coverage scopes and ranks are narrow.** Release-scope coverage aborts for releases created before the frozen `metadata_sha256` contract and for members outside the hard-coded accepted entity types; ranks are fixed to family/genus; per-rank thresholds are mandatory, must lie in [0,100] and are never defaulted or clamped; and a zero-row rank is fatal (`coverage.py`, `taxonomy.py`).
- **`operon taxonomy import` edits configuration before its transaction.** `config/schemas.yaml` is rewritten (entity-type and file-role values, ID pattern, version 1.3) before the import transaction starts, so the configuration edit survives a failed import. Imported sources are content-addressed (`{sha256}{suffix}`), a plain non-archive file is always classified as JSONL, and duplicate TaxIDs surface as a raw `sqlite3.IntegrityError` (exit 1) rather than a validation error (`taxonomy.py`).
- **Re-importing identical bytes under a new version label duplicates the identity.** The archived copy is reused but a second `files` row is registered, so residency and eviction bookkeeping sees two file identities for one artifact (`taxonomy.py`).
- **Name patterns and diagnostic dumps behave asymmetrically.** `exclude_name_patterns` are unanchored, case-sensitive `re.search` patterns: at compile time they are tested against target-rank candidate names and at report time against every lineage node name, so one pattern can silently remove a clade from both numerator and denominator. `merged.dmp`/`delnodes.dmp` are optional, so the same retired TaxID resolves as UNKNOWN, MAPPED_ALIAS or DELETED_TAXID depending on the import format, and taxonomy import accepts only local files — there is no URL, timeout or retry option (`taxonomy.py`, `coverage.py`).
- **Table import and metadata import disagree on CSV.** `operon table import` reads `.csv` with `csv.DictReader`, so `#` lines are data and a ragged row surfaces as `unknown field(s) [None]` instead of the structural comment and field-count rules used for TSV (`table_import.py`, `schema.py`).
- **The TUI Config screen restarts profile/recipe versioning when the file disappears.** Deleting or renaming `config/profiles/<name>.yaml` (or removing a recipe from `config/tools.yaml`) makes the editor read the current version as absent, so the next save writes **version 1** again; with unchanged content `INSERT OR IGNORE` quietly reuses the old snapshot, but changed content inserts a second row with `profile_version = 1`, so per-name versions stop being monotonic. The screen also cannot remove `max_hits_per_query` (clearing the field keeps the file value and reports "unchanged") (`tui/screens/config.py`, `tui/actions.py`).

## NCBI Datasets adapter

- **Imports can clear fields after all.** The adapter's merge check treats the source tokens `na`/`n/a`/`null`/`none` as non-empty, they are then normalized to NULL, and the upsert writes every column — so an existing value IS cleared to NULL and the clear is audited, contradicting the "add or update only" reading of the import path (`adapters/ncbi_datasets.py`, `schema.py`).
- **Some normalization is silent.** Unknown sex values become `unknown`; unparseable dates and out-of-range latitude/longitude become NULL — no errors or reason codes (`adapters/ncbi_datasets.py`).
- **Only `GCA_`/`GCF_` accessions are accepted** (optionally versioned, uppercased); SRA runs and other identifier schemes are hard validation errors (`adapters/ncbi_datasets.py`).
- **Partial download failures keep committed batches.** When some batches fail but others import, the run raises a validation error after the successful batches are committed; a rerun skips the completed batches idempotently (`adapters/ncbi_datasets.py`).
- **The pre-2.6 annotation bridge is conservative.** It reuses an existing annotation row only for the assembly's canonical accession and only when the row is not already claimed by a different accession — a workaround for paired GCA/GCF packages with identical annotation metadata but different GFF bytes (`adapters/ncbi_datasets.py`).
- **Disk-space preflight reserves a fixed 64 MiB** and stages downloads under the project root, never `/tmp` (`adapters/ncbi_datasets.py`).
- **The adapter auto-upgrades old metadata schemas.** Opening a pre-{{ metadata_schema }} `config/schemas.yaml` upgrades it in place, normalizing formatting and dropping hand-written comments (the same normalization the first remote-only eviction applies; see the [remote storage guide](../guides/remote-storage.md)) (`adapters/ncbi_datasets.py`).
- **An unversioned assembly accession re-downloads its archived package.** `_canonical_accession` keeps the version, so requesting `GCF_000001405` while the archived assembly is `GCF_000001405.40` makes `_assembly_asset_role` derive the alternate-source role `genome_fasta_refseq`; no manifest row carries it, the include counts as missing, and every run downloads the package again. Ingest stays idempotent, so this is wasted transfer rather than duplication — request the versioned accession to reuse the archive (`adapters/ncbi_datasets.py`).
- **`ncbi-reconcile` can apply changes without leaving a trace.** A planned accession-primary update whose accession row has disappeared is skipped silently, and a replayed supersession entry writes no audit record; both are correct for idempotence but invisible in `changes` (`ncbi_reconcile.py`).

## Backup and the import wizard

- **A failed database open leaks its connection.** When the DDL or a migration raises during `Database.__init__` (for example a corrupt `operon.sqlite`), the connection is never closed: the command exits 1 and the connection is only reclaimed by the garbage collector, emitting `ResourceWarning: unclosed database` (`database.py`).
- **`backup create` snapshots SQLite via the backup API.** The default `--scope` is `control`, and every scope — including `control` — embeds a complete SQLite snapshot taken with the backup API, so it stays consistent while other connections write and no WAL files are copied (`backup.py`, `cli.py`).
- **Scope `results` cannot restore your data.** It adds QC/analysis/reports/taxonomy/releases but excludes `raw/` and `standardized/`; only `full` includes data bytes, and the destination must be outside the project root and must not exist (see the [backup and migration guide](../guides/backup-migration.md)) (`backup.py`).
- **Backup coverage is silent about what it skipped.** Missing scope directories are skipped without a message, so a backup can succeed while omitting `releases/`; only files and symlinks are manifested and verified (empty directories are invisible), `verify` never opens the SQLite snapshot, and a manifest entry without `size_bytes`/`sha256` escapes as a raw `KeyError` traceback (`backup.py`).
- **Only some symlinks are rebased.** Absolute symlinks under `standardized/` that point inside the project are rewritten to relative targets when the backup is created; relative links, links elsewhere in the tree and absolute targets outside the project keep their exact text, and there is no restore command (`backup.py`).
- **`backup verify` rejects unexpected extra files**, not only missing or changed ones (`backup.py`).
- **The wizard holds the write lock while hashing and copying.** Ingest happens inside one large transaction; on failure the database rolls back, buffered JSONL records are discarded, and only newly created `raw/` targets are deleted — pre-existing targets stay (`import_wizard.py`).
- **The wizard re-hashes inputs, burns IDs and needs a user name.** Each input is hashed two to three times and the first pass runs outside the write lock; `db.next_id()` reserves and commits IDs while prompts are still open, so a cancelled wizard permanently burns IDs; the actor is `os.environ.get("USER")`, so container or cron runs record a NULL actor; and new entities are forced to `METADATA_VALIDATED` (`import_wizard.py`, `database.py`).
- **The wizard needs a TTY and accepts only regular files** (no directory artifacts). If another process consumes a shown ID in the meantime, preflight raises and the wizard must be restarted (`import_wizard.py`).
- **Known issue: the wizard breaks when its draft outlives the database state.** Repopulating a page assigns the draft's remembered IDs to the pickers; if an entity was retired or removed while the wizard was open, the `Select` value is no longer among the freshly loaded options and `InvalidSelectValueError` is raised on the UI thread inside the worker callback, so the page never renders and no inline error appears. For the same reason a failed startup leaves navigation enabled with an empty reserved-ID map, and pressing Next with a typed organism name then raises an uncaught `KeyError`. Leaving the sequencing/annotation page clears only the enable checkbox, so stale widget text can reappear when the section is re-enabled (`import_wizard.py`, TUI).
- **The demo project is byte-deterministic and deliberately broken.** The synthetic project uses a fixed seed (20260816), fixed contig lengths and 400×100 bp reads with hard-coded IDs (with a gap at `ANN_000002`), release `2026.08.demo` and project `PRJ_DEMO_001`; it ships a broken annotation (601-nt CDS, dangling mRNA parent), constant `'I'` read quality and an R2 that is unrelated random DNA rather than the reverse complement; its sources live in `examples/synthetic_source`, which `full` backups copy (`demo.py`, `backup.py`).
- **The demo registers proteins before their GFF3** so annotation QC sees complete annotation releases; file insertion order matters for multi-file entities (`demo.py`).

## Environment and shutdown

- **Local and remote environment documents differ by construction.** Local captures include the Python and `operon` versions that remote probes cannot report, so the same machine can produce different `environment_id`s for local versus SSH execution — and one local backend can produce two documents, because the in-process probe carries those versions while the launcher probe does not (`environment.py`, `environment_capture.py`, `execution.py`).
- **`environment_id` is whole-document, so host identity still separates environments.** Redaction replaces the hostname with a comparable `sha256:` digest but keeps it in the document, and the fingerprint hashes the whole document, so identical configurations captured on different hosts never deduplicate; only `relevance_fingerprint` ignores the hostname. Redaction happens at capture time (the remote probe file itself is written with `umask 077`) and pre-redaction documents are never migrated; the probe's `home` key is transient (see the [execution model](../architecture/external-analysis.md)) (`environment.py`, `execution.py`).
- **Redaction is shallow.** It walks only top-level strings and runs before document enrichment, so a `file://` Conda package URL keeps its absolute home path in the stored document and in the exported `@EXPLICIT` spec; the home-prefix pattern only matches at the start of a token, so `/mnt/data/home/u/x` survives, and `HOME=/` disables home redaction entirely (`environment.py`, `environment_capture.py`).
- **Capture status and flags enter the fingerprint.** `capture_status`, `capture_errors`, `capture_scope` and the hardware-capture flags are part of the hashed document, so one undecodable record gives an otherwise unchanged environment a distinct `environment_id`; Conda package URLs other than http/https/file are blanked, which forces `conda.status="partial"` and makes `export_conda` refuse (`environment_capture.py`).
- **Unsupported launchers and package metadata are stored verbatim.** Wrapper and container launchers, and unknown conda/mamba flags, are recorded as `unsupported_launcher` with `capture_scope: executor_only`; each package's full `depends` list and one base64 `conda-meta` record are stored with no size cap (`environment_capture.py`).
- **Environment degradation is recorded, not enforced.** Slurm and remote-Slurm backends have no pre-job probe, so a `strict` policy is downgraded and the run details record the ASCII literal `environment_policy_degraded: strict->warn`; when either side lacks sub-fingerprints the comparison is recorded as `environment_compare: unavailable`, where `warn` reuses as usual and `strict` also degrades to `warn` rather than invalidating the cache (see the [execution model](../architecture/external-analysis.md)) (`tools.py`, `environment.py`).
- **A second signal skips cleanup.** The first SIGINT/SIGTERM triggers graceful shutdown (exit code 130); a second signal during cleanup calls `os._exit(128+signum)` immediately. `graceful_shutdown` is a no-op outside the main thread (`shutdown.py`).
- **Known issue: a signal after a completed cleanup still force-exits.** `_cleanup_in_progress` is only cleared when the shutdown context manager exits, so any signal arriving after cleanup finished but before the context unwinds exits immediately with `128+signum` (`shutdown.py`).

## CLI conventions

- **Known issue: a ragged coverage report crashes the TUI viewer.** `data.read_coverage_report` returns rows verbatim, so a hand-edited `reports/coverage/COV_*/coverage_*.tsv` whose row has more fields than its header makes `CoveragePanel` raise `ValueError: More values provided than there are columns.` on the app thread instead of showing an inline error (`tui/screens/coverage.py`).
- **Exit codes:** 0 success; 1 runtime/SQLite/OSError (including `FileExistsError` from release/export) and any per-item failures in `qc`/`verify`/`analyze`/`push`/`pull`/`evict`/`backup verify`/`report coverage`; 2 for every `OperonError` (validation, conflict, checksum, remote, configuration); 130 for the first interrupt (with the message that progress was saved and the command can be re-run — true only for the resumable NCBI adapter and analysis paths); `128+signum` for a second signal (`cli.py`, `shutdown.py`). The mapping is by exception class, so an uncaught `sqlite3.Error`, `RuntimeError`, `OSError`, or `ValueError` from a handler also returns 1 with its message prefixed `error:`, even when the failure is a programming error rather than a runtime condition; exception types outside that chain (`KeyError`, `yaml.YAMLError`) escape as a traceback with exit 1. The resumable interrupt semantics behind exit 130 are documented under [analyze](cli-analysis.md#analyze).

## Deferred to the 1.0 release

Several development-era compatibility shims exist only for databases created before 1.0 and are scheduled for removal at 1.0 (marked `TODO(1.0)` in the code):

- The pre-1.0 migration call and `_migrate_pre_1_0_schema()` rebuild in `database.py` (legacy rows keep `legacy:` input identities and never dedupe against new QC rows).
- The adapter's defensive field projection for legacy schemas and its automatic metadata-schema upgrade in `adapters/ncbi_datasets.py`.

Other development-era shims carry no `TODO(1.0)` marker and are absent from that inventory: the pre-2.6 annotation bridge and legacy `_table_exists` guards in `adapters/ncbi_datasets.py`, the `config/schemas.yaml` rewrite applied on the first remote-only eviction (`remotes.py`), and the `location_identity` digest shim that preserves the pre-execution-backend digest for local runs (`tools.py`).

See [Database compatibility](../operations/database-compatibility.md) for the full inventory and the removal policy.

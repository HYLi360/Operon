# 性能预算

本页规定 Operon 的性能预算放在哪里、每项预算测量什么，以及一个数字如何才算生效。它的目的是把性能变成**可评审的决策**，而不是等第一位大项目用户替我们发现惊喜。

## 状态

**政策生效，基线尚未测量。** 在每一项预算同时带有实测基线与产生它的命令之前，本页任何数字都不构成承诺。第一次触及 TUI 数据路径的改动（进行中的视觉重构）预计产出 TUI 基线；`report view` 在其命令落地时获得基线。

在此之前，任何性能说法都视为未经核实。

## 预算目标

| 编号 | 目标 | 测量什么 | 测量对象 |
|------|------|----------|----------|
| PERF-1 | TUI 首帧 | `operon tui` → Home 面板完成组装并绘制（冷进程、OS 缓存已热） | 10⁴ 与 10⁵ 文件的夹具项目 |
| PERF-2 | TUI 面板切换 | 按键 → 目标面板完成绘制且数据已载入（同一会话内 ≥5 次切换取中位数） | 同上 |
| PERF-3 | 机读出口（`report view` bundle、`report … --format json/tsv --out`） | 从开始到产物完整、原子改名完成的墙钟时间 | 同上 |

每条预算都遵循两条规则：

- **预算是上限，不是平均值。** 测量定义为夹具上连续三次运行中的最差值，避免用"恰好命中缓存"达标。
- **预算必须能被第三方复现。** 记录里写明夹具、确切命令与测量机型。没有命令的数字不算基线。

## 夹具

夹具就是[内置 QC 性能诊断](qc-performance.md)描述的基准集合，并沿用同一套行数量级阶梯（10³ / 10⁴ / 10⁵ 文件）。确定性演示项目（`operon init-demo`）属于冒烟级夹具，除启动开销的回归之外太小，测不出别的东西。

## 数字如何入库

1. 在夹具上测量，并把命令写在数字旁边。
2. 基线写进本页（两种语言树同步），且与"把该数字写进测试或诊断脚本"的那次改动同批提交。
3. 若某次改动使测量值劣于已记录的预算，该改动**必须**要么修回归、要么带着理由更新预算——默默接受更慢的路径不是选项。
4. 只有用测量数据证明新值合理时，才允许抬高预算。

## 测量方法

测量必须脚本化——绝不手工——因为这些数字要在 pull request 里被评审。脚本目前尚不存在；**加入第一个预算数字与产生它的脚本必须在同一次改动里完成**。在该改动落地前，下面的配方是脚本预期采取的形状：

```bash
# 1. 构建夹具（确定性，每次同一种子）
operon init-demo <fixture-root>          # 冒烟级
# 10^4 / 10^5 文件夹具：见 operations/qc-performance.md

# 2. TUI 首帧 / 面板切换：在应用内部测量
#    （用 Textual pilot 跑一次：组装面板，并在第一帧绘制完成时停表——绝不用截图时间戳）
# 3. 机读出口
time operon report view --out /tmp/view_bundle
```

TUI 数字的仪表规则：

- 测**组装并绘制完成**，而不是"worker 已启动"：最典型的性能事故是某次数据查询卡住首帧。
- 从冷进程启动测量，因为 TUI 的查询与 tools 配置加载都发生在启动阶段。
- 绝不用截图或录屏测量：它们会引入一帧与被测代码路径无关的延迟。
